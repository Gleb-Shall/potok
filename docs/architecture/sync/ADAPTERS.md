# Своя авторизация и хранилище

По умолчанию `Site` открывает `App` без провайдера: локальные данные, без аккаунта и без запросов Firebase. Вход и облако выбирает сборка, которая подключает ядро. Существующая конфигурация Firebase сама по себе больше не включает облако.

## Точка подключения

```jsx
import { App } from '@potok/core';
import { createWorkspaceProvider } from '@potok/core/lib/workspace-provider.js';
import { authClient, workspaceApi } from './my-service.js';

// Один стабильный экземпляр на приложение, не внутри функции рендера.
export const provider = createWorkspaceProvider({
  id: 'my-service',
  name: 'Мой сервис',
  signInLabel: 'Войти в мой аккаунт',
  entryLabel: 'Продолжить',
  async connect() {
    return {
      auth: {
        subscribe: (changed, failed) => authClient.subscribe(changed, failed),
        signIn: () => authClient.signIn(),
        signOut: () => authClient.signOut(),
      },
      storage: {
        subscribe: (id, changed, failed) => workspaceApi.subscribe(id, changed, failed),
        read: id => workspaceApi.readFromServer(id),
        compareAndSwap: (id, next, revision) => workspaceApi.compareAndSwap(id, next, revision),
      },
    };
  },
});

// key также изолирует состояние при явном переключении между сервисами.
const screen = <App key={provider.id} provider={provider} initialMode="personal"/>;
```

`authClient` и `workspaceApi` здесь — реализации своего сервиса, а не готовые библиотеки Потока. Авторизацию можно реализовать формой пароля, OAuth, passkey, корпоративным входом или другим способом. Календарь вызывает `signIn()` непосредственно из обработчика клика, сохраняя возможность открытия окна входа. Для обязательного входа добавляется `requireAccount`; локальная сборка этого не требует.

## Контракт auth

- `subscribe(changed, failed)` сообщает текущий аккаунт и последующие изменения. Возвращает функцию отписки.
- Аккаунт: `{ id, displayName?, email?, photoURL? }`; `id` — непустая стабильная строка. Отсутствие аккаунта — `null`.
- `signIn()` и `signOut()` возвращают Promise. Способ входа принадлежит адаптеру.
- Токены и SDK-объекты остаются внутри адаптера. Ядро получает только идентификатор и сведения для отображения.

## Контракт storage

- `read(userId)` всегда читает авторитетное состояние сервера. Возвращает нормализованный workspace с целой неотрицательной `revision`. Кеш вместо сервера здесь недопустим.
- `subscribe(userId, changed, failed)` вызывает `changed(data, fromServer)`, возвращает функцию отписки. Первое состояние должно прийти даже без последующих событий. Для кеша `fromServer=false`; подтверждение сервера — `true`. При отсутствии push-транспорта минимумом служит первоначальный GET с корректной отменой; ручное обновление и проверка перед записью продолжают работать.
- `compareAndSwap(userId, next, expectedRevision)` **атомарно на сервере** проверяет текущую версию, записывает новое состояние с увеличенной версией и возвращает подтверждённый workspace. При несовпадении бросает `WorkspaceConflictError` из `workspace-provider.js`.
- Новое пустое пространство имеет `revision=0`. Формат календаря остаётся тем же: события, записи, шаблоны, повторы и остальные поля `normalizeData()`.

Backend самостоятельно проверяет владельца данных. Переданный `userId` и интерфейс приложения не заменяют серверную авторизацию. Для SQL подходит условный UPDATE по владельцу и версии в транзакции; для HTTP — проверка версии/If-Match, реализованная атомарно сервером. HTTP 409/412 адаптер преобразует в `WorkspaceConflictError`.

## Протокол каждого изменения

1. Календарь удерживает ревизию снимка, из которого подготовлено действие или открыт черновик.
2. `useWorkspace.save()` вызывает `saveWithFreshData()`: обязательный серверный `read` через сессию, затем сравнение с исходной ревизией.
3. При отличии запись не отправляется, редактор остаётся открыт и показывает ошибку. Свежие данные доступны для явного обновления; черновик автоматически не перезаписывается.
4. Если версии совпадают, выполняется `compareAndSwap`. Он снова проверяет версию на сервере: один GET перед обычным PUT не защищает от параллельной записи между ними.
5. Успех показывается после подтверждения. Ошибка чтения, отсутствие сети или смена аккаунта останавливают операцию. Поздние ответы прежней сессии игнорируются, включая A → B → A.

Все изменения через `App.commit` проходят этот путь: создание/удаление, перенос, подтверждение проведения, шаблоны, записи, напоминания, импорт и отмена. Локальный режим отдельно перечитывает ревизию из localStorage перед `persistData` и не обращается к облаку. Автоматического слияния конфликтующих черновиков пока нет.

## Дополнительные возможности

У провайдера могут быть `Settings` (компонент настроек), `notifications: { enabled, enable(user) }`, свой `explainError(error)`, `accountLabel`. У сервисов может быть `metadata` с необязательными `readSync(id)`/`rememberSync(id, at)` для отметки времени. Эти поля не участвуют в правах доступа и согласовании записей.

Сессия кешируется между монтированиями экрана, чтобы вход не мигал при переходах. `provider.dispose()` завершает подписки и сбрасывает кеш при окончательном отключении сервиса. Не вызывать его при каждом переходе с календаря на главную, если сессия должна оставаться прогретой.

## Необязательный Firebase-адаптер

`@potok/core/adapters/firebase/index.js` экспортирует `createFirebaseProvider({ config })`. Он использует Google Auth и транзакции Firestore; закрытый сайт выбирает его в собственном `src/cloud-provider.js`. Firebase SDK — необязательная peer dependency ядра, установленная как dev dependency для тестов адаптера. Сборка с этим адаптером добавляет `firebase` в собственные зависимости.

Реализация хранит существующий документ `users/{id}/workspaces/main`, формат payload и ревизии. Имя Firebase App по умолчанию остаётся `[DEFAULT]`, чтобы сохранить текущий кеш входа; для нескольких разных проектов можно передать отдельные `appName`. Старые пути `lib/firebase-client.js`, `cloud-config.js`, `cloud-workspace.js` оставлены как переходные экспорты. В новом коде используется явная инъекция провайдера.

Системный OAuth для Tauri и закрытые desktop-сборки относятся к следующим этапам. Выделение интерфейса подключения само по себе их не реализует.
