# Авторизация, хранение и синхронизация

## Граница ядра

`src/Site.jsx` открывает локальные личные данные без аккаунта. `App` принимает необязательный `provider`; закрытый сайт передаёт свой экземпляр из собственного `cloud-provider.js`. Ядро не выбирает сервис по переменной окружения и не импортирует SDK Firebase. Пользовательская авторизация и backend реализуются независимо за общим интерфейсом.

`src/lib/workspace-provider.js` содержит `createWorkspaceProvider`, общий `WorkspaceConflictError` и протокол `saveWithFreshData`. `auth` отвечает за аккаунт и вход, `storage` — за чтение, подписку и атомарную запись. Нормализованный пользователь имеет `id`, displayName/email/photoURL; SDK-объекты и токены не передаются в UI. [Полный контракт и пример](ADAPTERS.md).

`account-session.js` кеширует аккаунт и данные между монтированиями, отбрасывает старые ревизии и ответы другой сессии, управляет подписками. Провайдер живёт на уровне приложения; `dispose()` явно освобождает его при окончательном отключении. `useWorkspace.js` выбирает локальный/облачный режим и связывает сессию с редактором и состоянием синхронизации. `storage.js` хранит локальные данные и экспорт.

## Каждое облачное изменение

- Исходная ревизия берётся из рендера, на котором было подготовлено действие. Более новый снимок не делает старый черновик автоматически пригодным для перезаписи.
- `saveWithFreshData` обязательно вызывает серверное чтение. Ошибка сети или некорректная ревизия предотвращает запись.
- Если свежая ревизия отличается, сохранение отклоняется; ошибка видна внутри открытого редактора, поля черновика не меняются. Свежий снимок хранится отдельно до явного обновления.
- При совпадении вызывается серверный `compareAndSwap` с исходной ревизией. Backend обязан атомарно проверить версию ещё раз: GET и обычного PUT недостаточно.
- Подтверждение успеха приходит после ответа сервера. Поздние ответы прежнего аккаунта/провайдера игнорируются, включая A → B → A. Повторный клик не запускает параллельную запись.
- Кеш доступен для просмотра, но не выдаётся за серверное подтверждение. Офлайн-записи в облачном режиме не включены.
- Все действия App проходят общий commit/save: перенос, запись, шаблон, удаление, напоминание, импорт и отмена.

Локальная запись синхронно перечитывает ревизию из localStorage перед изменением. Формат расписания и JSON-резервных копий сохранён.

## Необязательный Firebase

`src/adapters/firebase/index.js` переводит Google Auth/Firestore в общий контракт. `config.js` хранит/валидирует клиентские идентификаторы; `workspace.js` читает payload и проверяет ревизии для транзакции; `notifications.js` обслуживает push через текущий Firebase App. Имя App `[DEFAULT]`, путь документа и ключи кеша сохранены, чтобы обновление не сбрасывало вход и данные. Старые `lib/firebase-client.js`, `cloud-config.js`, `cloud-workspace.js`, `push-notifications.js` — переходные пути импорта, ядро их не использует.

Правила доступа принадлежат Firestore Rules, а не кнопкам интерфейса. Открытый локальный dist не содержит Firebase SDK; закрытая сборка устанавливает SDK напрямую и передаёт адаптер явно. [Подключение своего Firebase](SELF_HOSTING.md).

## Ручная и автоматическая проверка

`SyncStatus.jsx` показывает последнюю успешную синхронизацию и вызывает `useWorkspace.sync()` → `connection.fetch()` без пересоздания аккаунта. Повторные нажатия делят запрос; без сети и во время сохранения проверка не запускается. При открытом редакторе свежая ревизия отмечается stale и не перезаписывает черновик.

Focus, online и возврат видимости запускают проверку, если последний подтверждённый ответ старше 30 секунд. Подписка адаптера может доставлять изменения непрерывно. Только серверный snapshot, успешный read или подтверждённая запись обновляют время. Ошибки и кеш этого не делают. Метаданные времени необязательны и не участвуют в согласовании.
